# MoA手動オーケストレーション — 小説推敲（整合性検証 + 読者視点評価）

**モデル管理・並列実行・例外処理・プロバイダ固有の注意点は [hermes-fake-moa](https://github.com/kgmkm/hermes-fake-moa) に集約されています。** 以下は小説推敲に特化した内容のみを記載します。

---

## 基本コマンド

hermes-fake-moa の `multi-chat.py` を使う場合:

```bash
python3 scripts/multi-chat.py --panel novel-revision --file prompt.txt --cwd /path/to/project
```

手動で `hermes chat -q` を使う場合:

```bash
hermes chat -q "プロンプト" -m "モデル名" --provider プロバイダ名 -Q --yolo --max-turns 2
```

## 4エージェント構成

各エージェントに**異なるLLM**を割り当てること（同一モデルでの複数視点はMoAの意味を損なう）。

| # | 視点 | 役割 | チェック内容 |
|---|------|------|-------------|
| 1 | **論理整合性** | プロット・伏線・キャラ行動の矛盾検出 | 時間軸、設定数値、因果関係、未回収伏線 |
| 2 | **文体・表現技法** | 比喩・五感・リズム・文体一貫性 | クリシェ、五感充足、説明的モノローグ、文長バランス |
| 3 | **時代考証・語彙** | 時代語彙・風俗検証 | 外来語、戦後俗語、度量衡、学術用語 |
| 4 | **読者視点評価** | 没入感・感情曲線・余韻評価 | 説明不足/過剰、共感阻害、幕切れ強度、希望/喪失バランス |

## エージェント指示テンプレート

### 必須要件

全エージェントの指示には以下を**必須**で含める：

1. **改善案の明示** — 問題指摘だけでなく、修正後の具体的な文章例を必ず添える
2. **場所の明示** — 章・節・行番号（該当テキスト引用付き）
3. **優先度付与** — 高/中/低

### テンプレート例（論理整合性）

```
以下の日本語小説の全章を精査し、論理整合性の問題を指摘せよ。
各指摘には**必ず改善案（修正後の具体的文章）を添える**こと。

ファイル:
- /path/to/novel/序章.md
- /path/to/novel/第1章.md
（...）

チェック項目:
1. 時間軸の矛盾
2. 設定数値の不整合
3. 未回収の伏線
4. キャラ行動の不自然さ

形式: 【章・節】【行】【問題点】【改善案（具体的文章）】【優先度】
```

### テンプレート例（文体・表現技法）

```
以下の日本語小説の全章を精査し、文体と表現技法の問題を指摘せよ。
各指摘には**必ず改善案（修正後の具体的文章）を添える**こと。

ファイル:
- /path/to/novel/全章.md

チェック項目:
1. クリシェ（陳腐な比喩・決まり文句）
2. 五感の偏り（視覚偏重で聴覚・触覚・嗅覚が不足していないか）
3. 説明的モノローグ（内面を説明しすぎていないか）
4. 文体の一貫性（三人称過去形が守られているか、キャラの口調が一貫しているか）
5. 文長のリズム（同じ長さの文が続いていないか）

形式: 【章・節】【行】【問題点】【改善案（具体的文章）】【優先度】
```

### テンプレート例（時代考証・語彙）

```
以下の日本語小説の全章を精査し、時代考証と語彙の問題を指摘せよ。
各指摘には**必ず改善案（修正後の具体的文章）を添える**こと。

ファイル:
- /path/to/novel/全章.md

時代設定: 【作品の時代設定を明記】

チェック項目:
1. 時代に存在しない語彙・概念（外来語、戦後俗語、現代技術用語など）
2. 舞台の文化圏に存在しない概念
3. キャラクターの知識範囲を超える語彙
4. 度量衡・通貨単位の時代整合性
5. 時代錯誤の比喩（VTR由来の「巻き戻る」等、後世の技術に基づく表現）

形式: 【章・節】【行】【問題語彙】【時代的理由】【改善案】【優先度】
```

### テンプレート例（読者視点評価）

```
あなたは一読者です。以下の日本語小説を読み、読者体験の質を評価せよ。
各指摘には**必ず改善案（修正後の具体的文章）を添える**こと。

ファイル:
- /path/to/novel/全章.md

チェック項目:
1. 読んで良かったと思える内容だったか？ 心に残る場面はあったか？
2. テーマ・モチーフが十分に表現されていたか？
3. 感情曲線通りに感情が動かされたか？
4. テーマをより深めるために改善できるシーン・キャラ行動の変更はあるか？
5. 説明不足で没入を阻害する箇所／説明過剰でテンポを損なう箇所
6. 幕切れの強度（読後に残る余韻の質）

形式: 【章・節】【行】【評価ポイント】【改善案（具体的文章）】【優先度】
```

## 合議集計

全エージェント完了後：

1. 4エージェントの全指摘を統合
2. 複数モデルが共通して指摘した項目を最優先
3. 単独モデルの独自発見も重要度に応じて採用
4. **改善案を横断比較**し、最も効果的な案を選定または合成
5. クロスモデル分析表を作成（どのモデルが何を指摘したか）
6. **【必須】集約した改善案の設定矛盾検出** — 改善案が作品の既存設定（年表、尾の本数と年齢の関係、キャラクターの過去、世界観ルール）と矛盾していないか照合する。LLMは設定の全体像を把握していないため、改善案に「500年前に9尾だった」といった設定違反が混入しうる。矛盾が検出された場合、改善案を修正するか、矛盾のない代替案をユーザに提示する
7. 最終修正リストをユーザに提示し、承認を得てから本文修正に着手する

**実例**: 名前の由来改善案に「九つの尾を持ちながら」→ 設定では50年/1尾で500年前の若い妖狐は2〜4尾。矛盾検出により「いつか九つの尾を揃える日を夢見る」に修正。
